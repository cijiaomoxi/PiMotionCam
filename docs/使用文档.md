## 1. 简介与特性

pikrellcam-lite 是一套运行在 Raspberry Pi 上的**移动侦测录像服务**：摄像头持续出帧，
画面出现移动时自动触发录像，录像结束后生成整帧缩略图与运动目标裁剪图，
用户通过浏览器里的管理界面完成调参、回看和运维。

它复刻了官方 [PiKrellCam](https://github.com/billw2/pikrellcam) 的网页功能，
并在其基础上做了若干增强。

### 与官方 PiKrellCam 的差异

官方 PiKrellCam 最后一次提交停在 2020 年，构建在已被 Debian 13 删除的旧相机栈（MMAL）之上，
在当前系统上无法编译运行。pikrellcam-lite 保留官方的使用体验，但换掉了底座：

| 方面 | 官方 PiKrellCam | pikrellcam-lite |
| --- | --- | --- |
| 相机栈 | MMAL（`/opt/vc`，仓库已下架） | libcamera / picamera2 |
| 运动检测 | BCM2835 硬件运动矢量 | 帧差分 + 邻域密度去噪 |
| 摄像头 | 仅 CSI | CSI **与** USB（UVC） |
| 原生加速 | 无 | C 内核（ctypes 加载），全链路约 4.7 倍加速 |
| 采集通路 | 固定 | 可在 ISP 硬件 JPEG 与原始 RGB 之间随时切换 |
| 异常自愈 | 无 | 取帧看门狗 + 自动降级（分辨率 → 帧率 → 回退 RGB888） |
| 版本管理 | 无 | 逐版本独立目录 + 一键回滚 |
| 界面语言 | 中文 | 中文 / 英文可切换 |

### 主要特性

- **实时预览**：multipart MJPEG 长连接预览，时间戳、FPS、区域框等 OSD 由浏览器叠加，不烧进图像。
- **图形化运动区域**：在预览画面上直接拖拽绘制矩形，可移动、缩放、重命名，支持多个区域。
- **双算法并行侦测**：`far`（远处小而慢的目标）与 `near`（近处大目标）各自独立配置灵敏度。
- **预录 / 补录**：触发瞬间自动带上之前若干秒的历史画面，不会漏掉"刚进来"的目标。
- **事件回看**：每个事件生成 MP4 录像 + 整帧缩略图 + 运动目标裁剪图。
- **磁盘自管理**：超过容量上限自动删除最旧的录像。
- **延时摄影**：按周期抓帧，结束后自动合成 MP4。
- **舵机云台**：RPi.GPIO / ServoBlaster / lgpio 后端自动探测，支持位置预设与限位。
- **定时命令**：按星期 + 时刻或固定间隔执行命令，支持网页配置、`at-commands.conf` 文件热重载与 FIFO 接口。
- **事件钩子**：运动开始 / 结束 / 抓图、延时结束等时机执行自定义命令。
- **USB 摄像头**：ffmpeg + V4L2 双后端，MJPEG 直通零转码。
- **版本管理**：每个版本独立保留，历史版本永不覆盖，随时回滚。
- **中英双语界面**：顶栏可随时切换语言，无需重启服务。

## 2. 系统要求与硬件准备

### 硬件

| 项目 | 要求 |
| --- | --- |
| 树莓派 | **Raspberry Pi 4**（推荐）。Pi 3B / Zero 也能跑，安装时会自动降到 640×480 @ 8fps。Pi 5 同样支持。 |
| 存储 | microSD 卡，16GB 以上 |
| 摄像头（二选一） | **CSI 排线摄像头**（如 ov5647），或 **USB / UVC 摄像头** |
| 网络 | 与浏览器处于同一局域网，能解析 `pi.local` |

### 系统

- Raspberry Pi OS（Debian 13 / trixie，64 位），或同源的 Debian 13 arm64。
- 需要 root 权限执行一次 `apt` 安装。

### 摄像头接线

**CSI 排线摄像头**

1. 给树莓派**断电**（务必断电，热插拔排线会损坏接口）。
2. 把排线从摄像头模块一侧插入模块的排线座，插到底。
3. 把排线的另一端插入树莓派板上的 CSI 摄像头接口，同样插到底，并压紧接口卡扣。
4. 排线有方向性，以摄像头和主板厂商的说明为准（通常蓝色加固面朝向电路板一侧）。
5. 排线不要折成直角，长期使用建议做一个固定支架。

**USB 摄像头**

直接插入树莓派的 USB 口即可，无需额外配置。系统会把它识别为 `/dev/videoN`。

> 提示：Debian 13 的 libcamera 只带树莓派专用的处理器，**枚举不到 USB 摄像头**。
> pikrellcam-lite 为此实现了 ffmpeg + V4L2 后端，USB 摄像头请在网页的"系统 → 摄像头"里手动选择。

### 确认摄像头被识别

接好线后，在树莓派上执行：

```bash
# CSI 摄像头：libcamera 是否能看到
libcamera-hello --list-cameras

# USB 摄像头：V4L2 节点与支持的格式
v4l2-ctl --list-devices
v4l2-ctl -d /dev/video0 --list-formats-ext
```

## 3. 安装

### 3.1 拷贝源码到树莓派

在**开发机**上执行（`PKC_KEY` 换成你的 SSH 私钥路径）：

```bash
scp -r -i ~/.ssh/id_ed25519_pi_mcode pikrellcam-lite pi@pi.local:~/
```

### 3.2 执行安装脚本

登录树莓派后运行：

```bash
ssh -i ~/.ssh/id_ed25519_pi_mcode pi@pi.local
bash ~/pikrellcam-lite/install.sh
```

安装脚本会依次完成：

1. 检查并安装缺失的系统包（`python3-venv`、`python3-picamera2`、`python3-numpy`、`python3-pil`、`ffmpeg`）。
2. 建立虚拟环境 `~/pikrellcam-lite/venv`（`--system-site-packages`，直接复用系统的 picamera2 与 numpy）。
3. 在虚拟环境里安装 Flask。
4. 把源码复制到版本目录 `~/pikrellcam-lite/releases/<时间戳>-v<版本>/`，并把 `current` 软链指向它。
5. 写入 systemd 用户服务 `~/.config/systemd/user/pikrellcam-lite.service` 并 `enable --now`。
6. 编译原生加速内核（失败会自动回落到纯 Python 实现，不影响使用）。
7. 执行 `loginctl enable-linger`，让**没有图形登录会话时也能开机自启**。

### 3.3 补充安装可选依赖

安装脚本会覆盖上面的基础依赖，但下面这两项需要你手动补装：

```bash
# rpicam-apps：CSI 的 "ISP 硬件 JPEG" 采集通路需要它（提供 rpicam-vid）
sudo apt-get install -y rpicam-apps

# gcc：编译原生加速内核需要
sudo apt-get install -y gcc

# libjpeg62-turbo-dev：原生内核的 JPEG 编码需要（build_native.sh 在缺失时会自动安装）
sudo apt-get install -y libjpeg62-turbo-dev
```

| 依赖 | 作用 | 缺失后果 |
| --- | --- | --- |
| `python3-venv` | 建立虚拟环境 | 安装脚本无法运行 |
| `python3-picamera2` | libcamera 通路 | CSI 摄像头不可用 |
| `python3-numpy` | 帧差分运算 | 服务无法启动 |
| `python3-pil` | 图像解码、缩略图 | 预览与缩略图不可用 |
| `ffmpeg` | 录像编码、延时合成、延时摄影 | **无法录像** |
| `rpicam-apps` | 提供 `rpicam-vid` | CSI 自动退到原始 RGB 通路（CPU 更高） |
| `gcc` | 编译 C 内核 | 自动回落到纯 Python 实现 |
| `libjpeg62-turbo-dev` | C 内核的 JPEG 编码 | 同上 |

### 3.4 验证安装

```bash
# 服务状态
systemctl --user status pikrellcam-lite.service

# 实时日志
journalctl _SYSTEMD_USER_UNIT=pikrellcam-lite.service -f

# 打开管理界面
# 浏览器访问 http://pi.local:8080/
```

### 3.5 开机自启

`install.sh` 已经执行过 `loginctl enable-linger`，一般不需要额外操作。手动确认：

```bash
loginctl show-user "$USER" --property=Linger
```

输出 `Linger=yes` 即表示未登录也会自动拉起服务。

## 4. 首次配置

### 4.1 打开管理界面

浏览器访问 **http://pi.local:8080/**。若 `pi.local` 解析失败，直接用树莓派的 IP 地址。

### 4.2 设置访问密码

进入 **系统** 标签页 → **升级与密码**：

- 在输入框里填入新密码并点"保存密码"，即启用密码保护。
- **留空**保存则关闭密码保护。
- 密码以 `sha256:<hex>` 形式保存在 `config.json` 的 `web.password_hash`，服务重启后仍然有效。
- 启用后访问任意页面都会跳转到登录页，未登录时调用 `/api/` 接口会返回 `401` 与 `{"auth": true}`。

> 忘记密码时见 [第 15 节](#15-常见问题排查)。

### 4.3 选择摄像头

进入 **系统** 标签页 → **摄像头**：

1. 在下拉框中选择目标摄像头（CSI 排线摄像头或 `/dev/videoN` 形式的 USB 摄像头），或保持"自动选择"。
2. 点"刷新列表"重新枚举设备。
3. 选择**采集通路**（见下表），点"切换"。

采集通路只有一个区别：JPEG 是在硬件里编码的，还是在 CPU 上编码的。

| 通路 | 含义 | 适用 | 备注 |
| --- | --- | --- | --- |
| 自动通路 `auto` | CSI 优先 MJPEG，USB 走 ffmpeg 直通 | 默认 | 推荐 |
| ISP 硬件 JPEG `MJPEG` | `rpicam-vid` 采集，ISP 硬件编码 JPEG，JPEG 字节直接透传给预览与录像 | CSI | 软件 JPEG 编码开销归零（`jpeg_ms = 0.0`），需要 `rpicam-apps` |
| 原始 RGB `RGB888` | picamera2 取原始帧，由本地 C 内核（libjpeg-turbo）编码 JPEG | CSI | 需要 90°/270° 旋转时自动切到此通路 |

在 **实时预览** 标签页里也有同样的一组下拉框和"切换"按钮，两处操作等价。

### 4.4 设置旋转与镜像

进入 **侦测调参** → **相机参数**：

- **旋转**：`0` / `90` / `180` / `270`。
  - `0` 与 `180` 由 ISP 直接完成，**零 CPU 成本**。
  - `90` 与 `270` 由 ISP 无法处理（需要 transpose），采集会自动改走原始 RGB 通路做软件旋转，CPU 占用略高。
- **镜像**：`none` / `horizontal` / `vertical` / `both`。

> USB 摄像头暂不支持旋转与镜像：USB 通路是 MJPEG 直通，做变换需要解码重编码。
> 设置了会在日志里提示"USB 摄像头暂不支持旋转/镜像"，配置值会被保留但画面不变。

### 4.5 确认画面正常

切到 **实时预览** 标签页，此时应该能看到连续刷新的画面，画面四角有 OSD 叠加层：

- 左上：时间与状态徽标（静止 / 移动）
- 右上：FPS、侦测 FPS、事件数、磁盘占用
- 左下：当前命中的算法、区域、变化占比、当前预设
- 右下：运动目标包围盒坐标

顶栏同时显示 FPS、侦测 FPS、事件数、磁盘占用与当前预设。

## 5. 界面导览

界面共六个标签页。

### 5.1 实时预览

左上是实时画面，右侧是运动区域与区域预设。

**画面区域**

- 画面上方两个下拉框：**摄像头选择** 与**采集通路选择**，配"切换"按钮。
- 画面下方的四个按钮：**暂停侦测**、**暂停录像**、**抓拍一张**、**重启服务**。
- 画面上覆盖的 OSD 是 HTML 叠加层，不影响录像画质。

**在预览画面上绘制检测区域**（重点操作）

| 操作 | 效果 |
| --- | --- |
| 在画面空白处**按住左键拖动** | 绘制一个新的矩形区域，松手即创建 |
| 在右侧区域列表中**点击一行** | 选中该区域（再点一次取消选中） |
| **拖动选中的框体** | 移动区域位置 |
| 拖动框体**右下角的小方块** | 缩放区域大小 |
| **双击框体** | 重命名该区域 |
| 区域列表里的"重命名 / 删除"按钮 | 重命名或删除指定区域 |
| 在区域列表下方输入名称后点"**新增整屏区域**" | 新增一个覆盖整幅画面的区域 |

补充说明：

- 拖动距离过小（小于画面的 1.5%）会被当作误点击而忽略。
- 区域数量上限 **32** 个。
- 新建的区域会自动命名为"区域 N"并**立即选中**，方便直接重命名或微调。
- 区域坐标以画面比例存储（0～1），因此切换分辨率后位置不会跑偏。
- 编辑后点"**保存区域**"写入配置；页面上多数操作也会自动保存。

**区域预设**

在"区域预设"面板里输入名称 → "保存当前为预设"，即可把当前这一组区域存成一个命名预设；
之后在下拉框里选中再点"载入"即可整体切换。

### 5.2 侦测调参

- **双算法灵敏度**：`far` 与 `near` 两组参数，详见 [第 6 节](#6-侦测调参详解)。
- **侦测开关**：启用移动侦测、启动即开始侦测（后者当前只保存该值，是否侦测实际由"启用移动侦测"决定）。
- **录像参数**：预录、补录、事件间隔、单事件最长、磁盘上限、剩余空间下限、编码质量 CRF、编码器。
- **相机参数**：主码流分辨率、帧率、旋转、镜像、侦测分辨率、侦测帧率、曝光（曝光滑块当前只保存数值，不会改变相机的自动曝光行为）。
- **成像参数**：亮度、对比度、饱和度、锐度、降噪、曝光模式、测光、曝光补偿、ISO、快门、白平衡、数字变焦，
  详见 [第 7 节](#7-成像参数矩阵)。
- **延时摄影参数**：启用开关、默认周期、启动后立即保持。
- 底部两个按钮：**保存配置** 与**恢复默认配置**。
- **配置预设**：把当前整份配置存成命名预设，一键激活。

> 修改分辨率、帧率、旋转、镜像、采集通路或摄像头会**重建采集管线**，画面会短暂中断几秒。

### 5.3 媒体

- **延时摄影**：填周期（秒）→"开始"；"保持"暂停抓帧；"结束并合成"把已抓的帧合成 MP4。
- **循环录像**：启用开关、每段时长、占用磁盘上限（%）、编码质量 CRF，
  以及"清空循环录像"按钮，详见 [第 7.1 节](#71-循环录像)。
- **事件录像**：列出所有事件，点击条目可查看；每条事件右侧有"归档到远端"按钮。
- **录像文件** / **抓拍图片**：两个文件列表，可直接点开。
- 顶部三个清空按钮：**清空录像**、**清空抓拍**、**全部清空**。

### 5.4 定时命令

- **新增 / 编辑定时命令**：星期、时刻、间隔（分钟）、命令内容、启用开关。
  - 星期支持 `*`、`Mon-Fri`、`Mon,Wed` 等写法。
  - **间隔大于 0 时优先于时刻**，即每 N 分钟执行一次。
- **命令列表**：表格展示全部定时命令，可逐条启用/停用/删除；"重新载入"按钮会重新读取配置与 `at-commands.conf`。
- **立即执行**：输入一条命令直接执行，输出显示在下方（仅支持[内部命令](#83-定时命令)）。

### 5.5 舵机

- **舵机状态**：显示当前后端、是否启用、当前角度、引脚与限位。
- **手动控制**：Pan / Tilt 滑块 + 平滑时间（毫秒），点"转到该位置"生效。
- **位置预设**：保存 / 调用 / 删除命名位置（如"中""左""右"）。

### 5.6 系统

- **服务控制**：启动 / 停止 / 重启服务。
- **摄像头**：设备与采集通路选择。
- **升级与密码**：一键升级（`git pull` + 重启）、访问密码设置。
- **版本与发布**：当前运行版本、`current` 指向、已保留的历史版本列表。
- **事件钩子**：四个钩子的命令输入框，保存后生效；下方显示最近 50 条钩子执行记录。
- **系统信息**：机型、系统版本、Python 版本、应用目录、媒体目录、主机名、运行时间。
- **帮助说明**：内置的功能概览。
- **实时日志**：每秒刷新的滚动日志，可开自动滚动、可清屏。

## 6. 侦测调参详解

### 6.1 检测原理

每一帧先降采样成灰度图（默认 320×180），与上一帧做绝对差，然后：

1. 按 `magnitude_limit` 二值化，得到"变化像素"；
2. 邻域密度滤波，滤掉孤立噪点（等价于官方的 "sparkle" 过滤）；
3. 在每个运动区域内统计变化像素占比，超过 `count_limit` 即命中；
4. 连续命中 `consecutive_frames` 帧才判定为移动。

两套算法**并行**运行，各自在每个区域内独立判定。

### 6.2 far 与 near 的区别

| 算法 | 面向目标 | 默认 `magnitude_limit` | 默认 `count_limit` | 默认 `consecutive_frames` | 默认 `noise_filter` |
| --- | --- | --- | --- | --- | --- |
| `far` | 远处、小而慢的目标 | 12 | 0.006 | 2 | 2 |
| `near` | 近处、大目标 | 28 | 0.02 | 2 | 3 |

- **`far` 更灵敏**：阈值低，对画面里缓慢移动的小目标（远处的人影、爬过的小动物）反应更快，也更容易被光照变化、飘动的窗帘干扰。
- **`near` 更保守**：阈值高，只对占据画面较大比例、变化剧烈的目标响应，适合门口、车道这种近距离场景。

**怎么选：**

- 监控远处通道、院子、阳台 → 主要用 `far`，必要时把 `near` 关掉以减少误报。
- 监控门口、车库等近距离场景 → 主要用 `near`。
- 两个都想兼顾 → 两个都开（默认状态），分别调各自的阈值。

### 6.3 参数含义

| 参数 | 含义 | 调大的效果 | 调小的效果 |
| --- | --- | --- | --- |
| `magnitude_limit` | **单像素灰度差阈值**。相邻两帧同一像素的亮度差超过它才算"变化"。 | 迟钝、抗噪 | 灵敏、易误报 |
| `count_limit` | **区域内变化像素占比阈值**。区域内变化像素数 ÷ 区域总像素数。 | 迟钝 | 灵敏 |
| `consecutive_frames` | **连续命中帧数**。要连续多少帧都命中才判定为移动。 | 迟钝、抗抖 | 灵敏、易误报 |
| `noise_filter` | **邻域去噪半径**。`0` 关闭；`k` 表示在 `(2k+1)×(2k+1)` 的邻域内，至少 1/4 的像素发生变化才算有效变化。 | 滤噪更强 | 保留更多细节 |

### 6.4 调参顺序建议

1. 先把 `motion.enabled` 打开，确认预览画面正常。
2. **先调 `count_limit`**，它是影响最大的参数（决定"多大动静算移动"）。
   - 误报多 → 提高 `count_limit`。
   - 漏报 → 降低 `count_limit`。
3. 误报仍然多 → 提高 `magnitude_limit`，或增大 `noise_filter`。
4. 画面本身抖动（风吹树叶、反光）→ 增大 `consecutive_frames` 到 3～5。
5. 把不需要的区域从检测范围里去掉：在预览上把区域改小，或在区域列表里把该区域停用。
6. 漏报远处的小目标 → 只调 `far` 的 `count_limit`，别去动 `near`。

> 帧差分对**整体光照突变**（开关灯、窗帘飘动）比较敏感。调高 `magnitude_limit` 与 `count_limit` 可以缓解。
> 另一个常见误报来源是**摄像头正对显示器**：屏幕内容变化会被当成移动。

## 7. 录像、循环录像与成像参数

### 7.1 录像流程

1. 服务持续维护一个**环形缓冲**，保存最近 `pre_seconds` 秒的 JPEG 帧。
2. 侦测命中时触发事件，把缓冲里的预录帧 + 当前帧一起写进 ffmpeg。
3. 移动结束后继续录制 `post_seconds` 秒。
4. ffmpeg 以 `image2pipe` 方式边收帧边编码，**不产生中间文件、不二次读盘**。
5. 事件结束后生成缩略图，写入事件索引。

因此"人刚踏进画面就走了"这类场景不会漏掉——触发瞬间之前的画面已经预录好了。

### 7.2 关键参数

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `pre_seconds` | 5 | 触发前预录秒数（0～30）。设为 0 表示不要预录。 |
| `post_seconds` | 8 | 触发后补录秒数（0～60）。移动停止后还会继续录这么久。 |
| `event_gap_seconds` | 10 | 两次事件之间的最小间隔。上一次事件结束后不到这个时间，新的移动不会触发新事件（避免连续抖动产生大量碎片录像）。 |
| `max_event_seconds` | 120 | 单个事件的最长时长（5～600）。持续移动时会强制结束，防止单个文件无限增长。 |
| `max_disk_gb` | 8 | **媒体配额**：录像 + 抓拍 + 延时占用的上限（GB，1～128）。超出后自动删除最旧的录像。设为 `0` 表示不限制。 |
| `min_free_gb` | 1 | **剩余空间下限**：目标文件系统可用空间低于此值（GB，0～20）时自动清理旧媒体；清理后仍不足则暂停录像并告警。`0` 关闭该护栏。详见 7.7。 |
| `encoder` | auto | 编码器，见下表。 |
| `quality` | 23 | `libx264` 的 CRF 值，10～40。数值越小画质越好、文件越大。硬件编码器不适用此项。 |

### 7.3 编码器选择

| 取值 | 说明 |
| --- | --- |
| `auto` | 检测到硬件 H.264 编码器（`/dev/video31` 存在或 `v4l2-ctl --list-devices` 里出现 `bcm2835-codec`）时用 `h264_v4l2m2m`，否则用 `libx264`。 |
| `h264_v4l2m2m` | 强制使用树莓派硬件编码器，码率固定 4 Mbps。Pi 4/5 推荐。 |
| `libx264` | 强制使用软件编码，按 `quality`（CRF）调节画质。 |

所有输出统一为 MP4（`yuv420p` 像素格式、`+faststart` 便于网页播放）。

### 7.4 产物

每个事件产生：

| 文件 | 位置 | 说明 |
| --- | --- | --- |
| `<事件ID>.mp4` | `media/videos/` | 事件录像 |
| `<事件ID>.jpg` | `media/stills/` | 整帧缩略图（320×180） |
| `<事件ID>_obj.jpg` | `media/stills/` | 运动目标包围盒裁剪图（240×240） |
| 索引条目 | `media/events.json` | 事件 ID、起止时间、时长、帧数、大小、编码器、命中的算法与区域 |

事件 ID 的格式是 `YYYYMMDD_HHMMSS`。

### 7.5 事件归档到远端

**媒体** 标签页里每条事件右侧有"归档到远端"按钮，也可以用 API：

```bash
# 归档单个事件
curl -X POST http://pi.local:8080/api/archive \
  -H 'Content-Type: application/json' \
  -d '{"id": "20261111_203015"}'
```

归档通过 `scp` 完成，目标地址取自配置 `media.archive_target`，形如 `user@host:/path`：

```json
{
  "media": {
    "archive_target": "pi@nas.local:/volume1/camera"
  }
}
```

要求树莓派上已配置好到目标主机的免密 SSH。**注意：归档目标目录必须事先存在且可写**，否则 `scp` 会失败并在界面上返回错误信息。

### 7.6 暂停录像

在 **实时预览** 页点"暂停录像"，或调用：

```bash
curl -X POST http://pi.local:8080/api/record \
  -H 'Content-Type: application/json' \
  -d '{"action": "pause"}'
```
录像恢复用 `{"action": "resume"}`（等价于 `"on"`）。

### 7.7 存储到 USB / 外接存储（v2.6.0+）

录像、抓拍和延时摄影可以写到 U 盘、移动硬盘或外接 SD 卡，而不是树莓派自带的 SD 卡。

**操作位置**：**媒体** 标签页 → **存储位置** 面板。选好设备后点 **应用存储设置**，**不需要重启服务**。

#### 为什么拔盘处理必须格外小心

U 盘拔掉之后，**挂载点目录还留在 SD 卡上**（只是变成了一个空目录）。
如果程序只判断"路径存不存在"，就会认为一切正常，录像继续往 SD 卡里写——
长期运行会把系统分区撑满，**树莓派变砖，无法启动**。

pikrellcam-lite 的处理方式：

| 检查项 | 说明 |
| --- | --- |
| 必须是挂载点 | 在 `/proc/mounts` 里查得到，普通目录不算 |
| 不能是根文件系统 | 防止误把 `/` 当成存储目标 |
| 实测可写 | 真的建一个临时文件，而不是只看权限位 |
| 写前校验 | **每次**开始录像前都重新校验一次 |
| 后台复查 | `StorageMonitor` 线程每 3 秒复查一次 |

#### 拔盘之后会发生什么

默认行为是**暂停录像 + 界面告警**（顶栏状态条变红，媒体页显示具体原因），**而不是**悄悄写回 SD 卡。

两个开关（存储位置面板上可勾选，也可以直接改 `config.json`）：

| 配置项 | 默认 | 含义 |
| --- | --- | --- |
| `media.require_mount` | `true` | 目标必须是真正的挂载点。关掉后可以用任意普通目录（不推荐） |
| `media.fallback_internal` | `false` | 设备拔出时是否回退到内置存储。设为 `true` 则拔盘后继续用 SD 卡录像，界面提示"已回退"，设备恢复后自动切回 |

事件索引 `events.json` **始终保存在内置存储**，所以拔掉 U 盘也不会丢事件列表。
（v2.5.0 及更早版本里索引是跟着 `media.dir` 走的，升级后会自动从旧位置读取。）

#### 命令行操作

```bash
# 查看检测到的存储设备与当前状态
curl -s http://pi.local:8080/api/storage

# 切到 U 盘（目录必须是当前真实挂载点，否则返回 400 并说明原因）
curl -X POST http://pi.local:8080/api/storage \
  -H 'Content-Type: application/json' \
  -d '{"dir":"/media/pi/USB","require_mount":true,"fallback_internal":false}'

# 切回内置存储
curl -X POST http://pi.local:8080/api/storage \
  -H 'Content-Type: application/json' \
  -d '{"dir":""}'
```

返回内容形如：

#### 手动挂载 U 盘

U 盘刚插上时系统可能还没自动挂载。可以先看一眼分区：

```bash
lsblk -f
```

必要时手动挂载：

```bash
sudo mkdir -p /media/pi/USB
sudo mount /dev/sda1 /media/pi/USB     # 分区名以 lsblk 输出为准
```

挂好之后回到 **媒体** 页点 **刷新列表**，设备就会出现在下拉框里。

> 提示：`/media/pi/USB` 只是常见约定，实际挂载点以 `lsblk -f` 和 `/proc/mounts` 为准。
> 存储面板下拉框里列出的是**系统当前真实的挂载点**，直接选即可。

#### 磁盘监测：配额和剩余空间是两回事

顶栏的「磁盘」指标显示的是**目标文件系统的真实剩余空间**（例如 `剩余 20.9 GB`），
低于下限时变红报警。「侦测调参」页的「录像参数」里同时显示媒体占用、配额、磁盘剩余。

| 配置项 | 默认 | 含义 |
| --- | --- | --- |
| `record.max_disk_gb` | `8` | **媒体配额**：录像 + 抓拍 + 延时占用的上限（GB，1～128）。超出后自动删除最旧的录像。`0` 表示不限制。 |
| `record.min_free_gb` | `1` | **剩余空间下限**：目标文件系统可用空间低于此值（GB，0～20）时开始清理旧媒体；清理后仍不足则暂停录像并告警。`0` 关闭该护栏。 |

**为什么需要两个参数**：配额可以调得比整块盘还大——一块 28.7 GB 的 SD 卡上设
`max_disk_gb = 128` 完全合法，但这时配额**永远不会触发**，录像会一路写到文件系统 100% 满。
ext4 根分区写满之后日志写不进去、配置存不下，设备可能直接开不了机。
真正兜底的是"还剩多少空间"，不是"攒了多少媒体"。

**清理顺序**（不会毁掉你的历史）：

1. 先删**最旧的录像**（连带它的两张抓拍），录像删完还有缺口才删**延时摄影**文件（可再生）；
2. **如果把全部媒体删光也补不上这个缺口**，说明磁盘是被别的东西占满的（系统日志、其它应用、其它分区），
   这时**一个录像都不删**，直接暂停录像并告警——保住历史比保住录像数量更重要；
3. 删了文件但空间没释放（空间被别的进程占着）时立刻停手，不继续删；
4. 每次自动清理都会写进服务日志：`disk guard: removed N old media file(s)`。

**切换存储目标后会重新检测**：切到外置盘后剩余空间按新目标重算——`POST /api/storage`
的响应里直接带 `disk` 段，后台每 3 秒复查一次，界面上每个候选设备都列出各自的可用 / 总量。

```bash
# 查看当前目标的剩余空间与护栏状态
curl -s http://pi.local:8080/api/storage | python3 -m json.tool

# 切换目标后会返回按新目标重算的检测结果
curl -s -X POST http://pi.local:8080/api/storage \
  -H 'Content-Type: application/json' \
  -d '{"dir":"/media/pi/USB"}' | python3 -m json.tool
```

响应中的相关字段：

```json
{
  "ok": true,
  "storage": {
    "disk_low": false,
    "disk_reason": "",
    "min_free_gb": 1.0,
    "usage": {"free": 22403497984, "free_human": "20.9 GB",
              "total": 30800916480, "total_human": "28.7 GB"}
  },
  "disk": {"total": 30800916480, "free": 22403497984,
           "used": 486040673, "low": false, "removed": 0, "reason": ""}
}
```

`GET /api/state` 的 `media` 段同样带这些数字（`disk_free_bytes` / `disk_free_human` /
`disk_total_bytes` / `disk_total_human` / `disk_low` / `disk_reason` / `min_free_gb`）。

### 7.8 循环录像（v2.7.0+）

**操作位置**：**媒体** 标签页 → **循环录像** 面板。勾选"启用循环录像"，设定每段时长与占用上限，点
**保存循环录像设置**即可，**不需要重启服务**。

开启后相机会持续录像，并按设定的时长切成一段一段，存放在 `media/loop/`（文件名形如
`loop_20261113_183143_0001.mp4`）。

| 配置键 | 默认 | 含义 |
| --- | --- | --- |
| `loop.enabled` | `false` | 是否启用 |
| `loop.segment_seconds` | `60` | 每段时长（秒），范围 5–3600 |
| `loop.max_disk_percent` | `30` | 循环录像最多占**整块文件系统**的百分比（1–95） |
| `loop.quality` | `26` | 循环录像的 CRF（10–40） |

命令行也可以：

```bash
# 打开 / 关闭 / 查询
curl -X POST http://pi.local:8080/api/loop -H 'Content-Type: application/json' -d '{"action":"start"}'
curl -X POST http://pi.local:8080/api/loop -H 'Content-Type: application/json' -d '{"action":"stop"}'
curl -s http://pi.local:8080/api/loop

# 改参数
curl -X POST http://pi.local:8080/api/loop -H 'Content-Type: application/json' \
  -d '{"segment_seconds":120,"max_disk_percent":20}'
```

内部命令（定时命令 / FIFO / at-commands 都能用）：`loop on`、`loop off`、`loop status`。

> **录像被暂停时，循环录像也不会录。** 网页上的"暂停录像"以及内部命令 `record off` 会停掉包括循环录像在内的
> 全部录像，这与官方上游 `pause` 的语义一致。面板会在状态标签旁直接显示"录像已暂停"，不会让你以为开关没生效。
>
> 面板还会显示**实际录像帧率**。它不一定等于你配置的 `camera.fps`：有些 USB 相机会无视请求帧率
> （配置 10 fps、实给 30 fps），这时采集侧会按配置节流，录像时间轴按**实测**帧率打点，
> 所以"每段 60 秒"的段，文件时长就是 60 秒左右，而不是 180 秒。

#### 循环录像和事件录像不会同时录

树莓派的 H.264 硬件编码器在 `/dev/video31` 上，**同一时刻只能有一个 ffmpeg 实例**用它；
采集线程也是单线程喂一路编码器。所以两路录像在硬件层面就不可能并行，
本实现按**状态互斥**处理（与官方上游的 `VCB_STATE_LOOP_RECORD` / `VCB_STATE_MOTION_RECORD` 一致）：

```
平时       → 循环录像写盘
检测到移动 → 收尾当前循环段 → 事件录像接管硬件编码器
事件结束   → 循环录像自动恢复（下一帧开新段）
```

因此同时开着"循环录像"和"移动侦测"时，事件发生的那几秒画面属于**事件录像**，不在循环段里。
这是硬件约束，不是取舍。

#### 磁盘满了先回收哪一类

v2.6.0 的两道护栏（媒体配额、剩余空间下限）也会回收循环录像段，**顺序是**：

**循环段 → 事件录像 → 延时摄影**

循环录像本来就是覆盖式录像，"旧的让位给新的"正是它的语义；事件录像带着具体的触发时刻，
优先级高于循环段。自动清理同样会写进服务日志（`loop guard: removed N old loop segment(s)`）。

### 7.9 成像参数矩阵（v2.7.0+）

**操作位置**：**侦测调参** 标签页 → **成像参数** 面板。调好滑块和下拉框后点 **应用成像参数**。

面板上的控件是**按后端返回的参数表自动生成的**，所以界面上多一个少一个参数，
都不需要改模板——参数表在 `core/imaging.py` 的 `SPECS` 里。

| 参数 | 范围 | 正常值 | 说明 |
| --- | --- | --- | --- |
| 亮度 `brightness` | 0～100 | 50 | 整体明暗 |
| 对比度 `contrast` | -100～100 | 0 | 明暗对比强度 |
| 饱和度 `saturation` | -100～100 | 0 | 拉到 -100 就是纯黑白（ISP 免费提供） |
| 锐度 `sharpness` | -100～100 | 0 | 边缘锐化 |
| 降噪 `denoise` | auto / off / cdn_fast / cdn_hq | auto | 夜间噪点多时调高 |
| 曝光模式 `exposure` | normal / sport | normal | sport 会缩短曝光时间 |
| 测光 `metering` | centre / spot / average / custom | centre | 决定自动曝光参考哪部分画面 |
| 曝光补偿 `ev` | -10～10 | 0 | 正数变亮、负数变暗 |
| ISO 增益 `iso` | 0～3200 | 0（自动） | 固定模拟增益 |
| 快门 `shutter` | 0～500000 µs | 0（自动） | 固定快门时间 |
| 白平衡 `awb` | auto / daylight / cloudy / … | auto | 夜间色偏时选固定色温 |
| 红 / 蓝增益 `awb_r_gain` / `awb_b_gain` | 0～3 | 0（自动） | 手动白平衡微调 |
| 数字变焦 `zoom` | 100～300 % | 100 | 中心裁剪放大，会损失分辨率 |

取值范围与官方上游的 MMAL 版本语义对齐，方便迁移配置。

#### 三条采集通路，三种生效方式

| 当前通路 | 参数怎么落地 | 改完要重启吗 |
| --- | --- | --- |
| CSI + rpicam-vid（ISP 硬件 JPEG） | 转成 rpicam-vid 命令行参数 | **要**，这些是启动参数，会重启采集进程（画面短暂中断） |
| CSI + picamera2 / libcamera（原始 RGB） | `set_controls()` | 不用，热更新 |
| USB 摄像头 | `v4l2-ctl --set-ctrl` | 不用，热更新 |

USB 摄像头支持哪些参数**必须现查**：先用 `v4l2-ctl --list-ctrls` 列出控件与量程，
再把统一参数线性映射到每个控件自己的范围；摄像头没有的控件会被跳过，
并在界面上置灰标注"当前采集通路不支持"。

命令行：

```bash
# 查看当前成像参数、通路与哪些项不支持
curl -s http://pi.local:8080/api/imaging | python3 -m json.tool

# 保存并应用
curl -X POST http://pi.local:8080/api/imaging -H 'Content-Type: application/json' \
  -d '{"values":{"brightness":60,"contrast":10,"awb":"daylight","saturation":-100}}'
```

> **未实现**：官方上游的 21 种 MMAL 图像特效（油画、卡通等）与色彩效果。
> 那些是 MMAL 专有功能，libcamera / rpicam-vid / V4L2 都没有对应实现，
> 用软件做则需要每帧解码再编码，与本项目"每帧零额外开销"的原则冲突。
> 监控场景真正用得上的**黑白**已由 `saturation=-100` 覆盖。

## 8. 延时摄影、舵机、定时命令、事件钩子

### 8.1 延时摄影（Timelapse）

**在网页上配置**：**媒体** 标签页 → 延时摄影面板；或 **侦测调参** → 延时摄影参数（默认周期、启动后立即保持）。

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `timelapse.enabled` | `false` | 是否启用延时摄影功能 |
| `timelapse.period` | 30 | 默认抓帧间隔（秒） |
| `timelapse.hold` | `false` | 启动后是否立即进入"保持"状态（保持时不抓帧） |

**操作流程**：

1. 填入周期（秒），点"开始"。抓帧会写入 `media/timelapse/<会话ID>/frame_00000.jpg`。
2. 点"保持"暂停抓帧，再点一次恢复。
3. 点"结束并合成"，把已抓的帧用 ffmpeg 合成 `media/videos/timelapse_<会话ID>.mp4`（libx264，CRF 23），随后删除临时帧目录。

成片帧率取 `round(1 / 周期)`，至少 1 fps。

**用命令控制**：

```bash
curl -X POST http://pi.local:8080/api/timelapse \
  -H 'Content-Type: application/json' \
  -d '{"action": "start", "period": 30}'
```

`action` 可取 `start`（可带 `period`）、`hold`（可带 `on`）、`end`。

### 8.2 舵机（Servo）

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `servo.enabled` | `false` | 是否启用舵机 |
| `servo.backend` | auto | 后端：`auto` / `lgpio` / `rpi` / `servoblaster` / `none` |
| `servo.pan_pin` | 18 | 平移舵机 BCM 引脚 |
| `servo.tilt_pin` | 17 | 俯仰舵机 BCM 引脚 |
| `servo.pan_min` / `pan_max` | 0 / 180 | 平移角度限位 |
| `servo.tilt_min` / `tilt_max` | 0 / 180 | 俯仰角度限位 |
| `servo.smooth_ms` | 0 | 平滑移动时间（毫秒），0 表示瞬间到位 |
| `servo.positions` | 3 个预设 | 位置预设列表，`[{name, pan, tilt}]` |

**后端自动探测顺序**：`RPi.GPIO` → `servoblaster` → `lgpio` → 不可用。都没有时舵机功能优雅降级，不影响其它功能。

**网页操作**：**舵机** 标签页 → "启用舵机"后，用 Pan / Tilt 滑块调角度，点"转到该位置"；填入名称后点"保存为位置预设"保存当前角度。

**命令接口**：

```bash
curl -X POST http://pi.local:8080/api/servo \
  -H 'Content-Type: application/json' \
  -d '{"action": "set", "pan": 90, "tilt": 45}'
```

`action` 可取 `enable`、`disable`、`goto`（带 `name`）、`set`（带 `pan`/`tilt`/`smooth_ms`）、`save_position`、`delete_position`。

### 8.3 定时命令

有三种等价的配置方式。

**(a) 网页界面**：**定时命令** 标签页 → 新增/编辑 → 保存。

**(b) 配置文件**：`~/.pikrellcam/at-commands.conf`，**热重载，无需重启**：

```
Mon-Fri 07:30 "@tl_start 30"
Mon-Fri 09:00 "@tl_hold off"
Fri 18:00 "@tl_end"
Mon 7:30 "record on"
```

格式为 `<星期> <时刻或间隔分钟数> "<命令>"`；星期支持 `*`、`Mon-Fri`、`Mon,Wed`；时刻不含 `:` 时按"固定分钟间隔"处理。以 `@` 开头的命令交给内部命令处理器，否则按普通命令处理。

> **注意：定时调度器只执行上面列出的内部命令。** 无法识别的命令会返回 `unknown command: …` 并**不会**被当作 shell 命令执行。需要执行任意的 shell 命令，请改用[事件钩子](#84-事件钩子)。

**(c) FIFO**：外部脚本可以往 `~/.pikrellcam/commands.fifo` 写入命令（不需要 `@` 前缀）：

```bash
echo "record off" > ~/.pikrellcam/commands.fifo
```

**可用的内部命令**：

| 命令 | 作用 |
| --- | --- |
| `record on` / `record off` / `record pause` | 开关 / 暂停录像 |
| `record_pause` | 暂停录像（同上） |
| `still` | 抓拍一张当前帧 |
| `tl_start [秒]` | 开始延时摄影，可指定周期 |
| `tl_hold on` / `tl_hold off` | 保持 / 恢复抓帧 |
| `tl_end` | 结束延时摄影并合成 |
| `loop on` / `loop off` / `loop status` | 开关 / 查询循环录像 |
| `imaging` | 查看当前成像通路与部分参数（只读） |
| `motion_enable on` / `off` / `toggle` | 开关移动侦测 |
| `motion load_regions 名称` | 载入命名区域预设 |
| `motion limits <magnitude_limit> <count_limit>` | 修改 far 算法的两个阈值 |
| `servo goto 名称` | 转到位置预设 |
| `servo set <pan> <tilt>` | 直接设定角度 |
| `servo enable` | 启用舵机 |
| `start` / `stop` / `restart` | 启停整个服务 |

也可以在命令前加 `@` 前缀（会被自动去掉）。**命令只能是上表中的内部命令**：无法识别的命令会返回 `unknown command: …`，不会被当作 shell 命令执行。

**立即执行**一条命令：

```bash
curl -X POST http://pi.local:8080/api/command \
  -H 'Content-Type: application/json' \
  -d '{"command": "record on"}'
```

### 8.4 事件钩子

在 **系统** 标签页 → **事件钩子** 里配置四个钩子：

| 钩子 | 触发时机 |
| --- | --- |
| `on_motion_begin` | 事件开始录像的瞬间 |
| `on_motion_end` | 事件结束 |
| `on_motion_preview_save` | 事件成功落盘并生成缩略图后 |
| `on_timelapse_end` | 延时摄影结束并合成后 |

命令里可以用占位符，触发时会被替换成实际值：

| 占位符 | 含义 |
| --- | --- |
| `{id}` | 事件 ID（如 `20261111_203015`） |
| `{video}` | 录像文件名 |
| `{thumb}` | 缩略图文件名 |
| `{duration}` | 事件时长（秒） |
| `{algorithm}` | 命中的算法（`far` / `near`） |
| `{region}` | 命中的区域名称 |
| `{time}` | 当前时间 `HH:MM:SS` |
| `{date}` | 当前日期 `YYYY-MM-DD` |
| `{media_dir}` | 媒体根目录 |
| `{stills_dir}` | 抓拍目录 |
| `{videos_dir}` | 录像目录 |

示例：

```
echo "移动开始: {id} 算法={algorithm} 区域={region} 时间={time}" >> /tmp/motion.log
curl -s -X POST http://192.168.1.10:8080/api/command -d '{"command":"record on"}'
```

钩子在独立线程里执行，单次超时 120 秒；执行记录（命令、状态、返回码、输出）在 **系统** 页的钩子历史里可以看到。

| `schedules` | `[]` | 定时命令数组。每项包含 `days`（星期）、`time`（时刻 `HH:MM`）、`interval_minutes`（固定间隔分钟数，>0 时优先）、`command`、`enabled`。 |

### 9.10 presets —— 配置预设

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `presets` | `{}` | 命名配置预设，值为一份配置片段。激活时合并进当前配置；分辨率或帧率发生变化时自动重启采集。 |

### 9.11 手工改配置

```bash
# 改端口
python3 - <<'EOF'
import json, pathlib
p = pathlib.Path.home()/"pikrellcam-lite/config.json"
c = json.loads(p.read_text()); c["web"]["port"] = 8090
```

配置文件由服务自动热重载（定时命令与区域预设即刻生效）；但涉及采集链路的键（分辨率、帧率、旋转、镜像、通路、设备）需要重启服务才会生效。

## 11. 多语言

v2.5.0 起，界面支持简体中文与英文，可随时切换。

### 11.1 切换方式

**方式一：网页顶栏的语言下拉框**。选好即生效，**无需重启服务**。

**方式二：修改配置文件**。编辑 `~/pikrellcam-lite/config.json`：

```json
{
  "web": {
    "language": "en-US"
  }
}
```

| 取值 | 含义 |
| --- | --- |
| `auto` | **默认**。按浏览器发送的 `Accept-Language` 请求头自动选择：浏览器偏好英文就显示英文，其余情况显示简体中文。 |
| `zh-CN` | 固定简体中文。 |
| `en-US` | 固定英文。 |

**方式三：调用 API**：

```bash
# 读取当前语言与文案字典
curl -s http://pi.local:8080/api/i18n | python3 -m json.tool

# 切换为英文（会持久化到 config.json）
curl -X POST http://pi.local:8080/api/i18n \
  -H 'Content-Type: application/json' \
  -d '{"language": "en-US"}'

# 恢复自动选择
curl -X POST http://pi.local:8080/api/i18n \
  -H 'Content-Type: application/json' \
  -d '{"language": "auto"}'
```

`POST /api/i18n` 的返回值包含 `language`、`available` 与 `strings`；传入未登记的语言代码会返回 `400` 与错误信息，传入 `auto` 则按当前请求的 `Accept-Language` 重新解析。

### 11.2 语言包文件

语言包位于 `core/locales/` 目录，是扁平的 JSON 字典：

```
core/locales/zh-CN.json
core/locales/en-US.json
```

结构形如：

```json
{
  "app.title": "pikrellcam-lite",
  "tab.preview": "实时预览"
}
```

语言包由前后端共用：后端用它翻译自己产生的提示消息，前端通过 `GET /api/i18n` 拿到整包后在浏览器里做替换。缺失的键会自动用兜底语言（简体中文）补齐，不会显示成空白。

### 11.3 新增一种语言

1. 复制一份 `core/locales/zh-CN.json`，改成新的语言代码，例如 `ja-JP.json`，并翻译其中的文案。
2. 在 `core/i18n.py` 的 `LANGUAGES` 字典里登记一行：

```python
LANGUAGES: dict[str, dict[str, str]] = {
    "zh-CN": {"name": "Chinese (Simplified)", "native": "简体中文"},
    "en-US": {"name": "English", "native": "English"},
    "ja-JP": {"name": "Japanese", "native": "日本語"},
}
```

3. 重启服务即可。新语言会自动出现在顶栏的语言下拉框里，也可以用 `{"language": "ja-JP"}` 直接切换。

> 匹配是宽松的：`ja`、`ja-jp`、`ja_JP` 都会被识别到 `ja-JP`；`zh`、`zh-cn`、`zh-hans` 都会被识别到 `zh-CN`。

## 12. 版本管理与回滚

### 12.1 目录结构

```
~/pikrellcam-lite/
├── current -> releases/20261110-2328-v2.4.0   # 软链，指向当前运行版本
├── releases/                                   # 所有历史版本，各自独立完整
│   ├── 20261110-2327-v2.4.0/
│   └── 20261110-2328-v2.4.0/
├── media/                                       # 录像 / 抓拍 / 事件索引（共享）
│   ├── videos/
│   ├── stills/
│   ├── timelapse/
│   └── events.json
├── logs/                                        # 运行日志（共享）
├── venv/                                        # Python 虚拟环境（共享）
└── config.json                                  # 配置（共享）
```

**版本目录与共享数据的边界**：

- **属于版本目录**：源码、`templates/`、`static/`、`core/`（含语言包与 C 内核产物）、各版本的脚本。
- **属于共享根目录**：`media/`、`logs/`、`venv/`、`config.json`。

因此升级和回滚**都不会丢录像、不会丢设置**，也不会让每个版本各写一份数据。

### 12.2 发布新版本

在**开发机**上执行（`PKC_HOST` 与 `PKC_KEY` 可用环境变量覆盖）：

```bash
# 发布当前工作目录
bash deploy.sh

# 列出远端已保留的全部版本 + 当前运行版本
bash deploy.sh --list

# 回滚到指定历史版本（按版本号匹配最新一个目录）
bash deploy.sh --rollback v2.4.0
```

默认目标主机是 `pi@pi.local`，私钥是 `~/.ssh/id_ed25519_pi_mcode`：

```bash
PKC_HOST=pi@pi.local PKC_KEY=~/.ssh/id_ed25519_pi_mcode bash deploy.sh
```

`deploy.sh` 的动作：

1. 打包当前目录（排除 `versions/`、`__pycache__`、`*.pyc`、`deploy.sh`）。
2. 通过 ssh + tar 上传到 `~/pikrellcam-lite/releases/<时间戳>-v<版本>/`。
3. 把 `current` 软链指向新目录，`daemon-reload` 并重启服务。
4. 在远端编译原生加速内核，失败则自动回落到纯 Python 实现。
5. 打印当前版本与服务状态。

**绝不覆盖**：发布目录名精确到分钟，同一分钟内重复发布会自动追加 `-r2`、`-r3` 后缀，历史版本原封不动保留。

### 12.3 手动回滚

```bash
# 在树莓派上执行
ln -sfn releases/20261110-2327-v2.4.0 ~/pikrellcam-lite/current
systemctl --user restart pikrellcam-lite.service
```

### 12.4 查看版本信息

- 网页：**系统** 标签页 → **版本与发布**。
- API：`GET /api/release` 返回 `{version, release, current, releases, root}`。
- 命令行：`bash deploy.sh --list`。

### 12.5 首次安装 vs 版本化发布

- **首次安装**：把源码拷到树莓派后运行 `bash ~/pikrellcam-lite/install.sh`，脚本会同时完成安装与"发布第一个版本"。
- **后续升级**：一律用 `deploy.sh` 发布，不要在树莓派上直接改代码——直接改会被下一次发布覆盖。

## 14. 原生加速说明

### 14.1 它是什么

pikrellcam-lite 把帧处理链路里最耗时的三段从 Python/numpy 挪进了 C：

| 内核函数 | 作用 |
| --- | --- |
| `pkc_gray_ds()` | RGB888 → 降采样灰度图 |
| `pkc_detect()` | 帧差分运动检测全流水线（双算法、密度滤波、区域占比、包围盒） |
| `pkc_jpeg()` | RGB888 → JPEG（libjpeg-turbo） |

源文件在 `core/_pkc_native.c`，编译产物是 `core/_libpkc.so`，由 `core/native.py` 通过 ctypes 加载。

**加速是可选的**：编译产物缺失、加载失败或平台不兼容时，服务自动回落到纯 Python + numpy 实现，**功能完全一致，只是慢一些**。

### 14.2 编译

```bash
# 在版本目录里编译（产物写到 core/_libpkc.so）
bash build_native.sh

# 强制重新编译
bash build_native.sh --force
```

需要 `gcc` 与 `libjpeg62-turbo-dev`（缺后者时脚本会自动 apt 安装）。在 aarch64 上会显式打开 NEON 指令集。

`install.sh` 与 `deploy.sh` 都会自动执行这一步。

### 14.3 查看当前后端

```bash
# 方法一：看日志
journalctl _SYSTEMD_USER_UNIT=pikrellcam-lite.service -n 50 | grep -i native

# 方法二：直接问 Python
cd ~/pikrellcam-lite/current
~/pikrellcam-lite/venv/bin/python -c "import sys;sys.path.insert(0,'.');from core import native;print(native.backend())"
```

输出 `native` 表示正在使用 C 内核，`python` 表示处于回落状态。
日志里也会出现 `native acceleration enabled (...)` 或 `native acceleration unavailable, falling back to pure python`。

### 14.4 关闭原生加速

临时关掉加速做对比或排障时，设置环境变量 `PKC_NO_NATIVE=1`：

```bash
# 只影响本次启动
PKC_NO_NATIVE=1 ~/pikrellcam-lite/venv/bin/python ~/pikrellcam-lite/current/krellcam.py

# 或写入 systemd 服务
systemctl --user edit pikrellcam-lite.service
```

在编辑器里加入：

```ini
[Service]
Environment=PKC_NO_NATIVE=1
```

然后：

```bash
systemctl --user daemon-reload
systemctl --user restart pikrellcam-lite.service
```

恢复时把这段删掉再 `daemon-reload` + `restart` 即可。

### 14.5 性能参考

树莓派 4，1280×720，检测分辨率 320×180：

| 环节 | 纯 Python | 原生 C | 加速比 |
| --- | --- | --- | --- |
| 灰度降采样 | 35.77 ms | 0.85 ms | 42.1x |
| 双算法运动检测 | 22.76 ms | 2.26 ms | 10.1x |
| JPEG 编码 | 18.62 ms | 13.29 ms | 1.4x |
| **单帧全链路** | **77.16 ms** | **16.40 ms** | **4.71x** |

C 内核与纯 Python 实现经过逐位比对：帧差分占比、包围盒、连续命中计数完全相同；JPEG 输出字节数相同、PSNR > 138 dB（视觉等同）。

> 注意：走 **ISP 硬件 JPEG** 通路时，JPEG 编码根本不在 CPU 上做（`jpeg_ms = 0.0`），此时 C 内核只负责灰度降采样与检测。

## 15. 常见问题排查

### 15.1 画面黑屏

1. **确认摄像头被识别**：`libcamera-hello --list-cameras`（CSI）或 `v4l2-ctl --list-devices`（USB）。
2. **确认选对了设备**：网页 **系统** → **摄像头**，看"摄像头详情"里的后端与格式是否正常。
3. **换一条采集通路**试：ISP 硬件 JPEG ↔ 原始 RGB，看哪条能出图。
4. **看日志**：`journalctl _SYSTEMD_USER_UNIT=pikrellcam-lite.service -f`，搜索 `error`。
5. **摄像头前端超时**（日志出现 `Camera frontend has timed out!`）：传感器已卡死，**必须断电复位**——拔掉电源等 10 秒再插上。树莓派的 `reboot` 不会切断 3.3V 电源轨，重启无效。

### 15.2 画面卡住不动

1. **先等一会儿**：服务内置取帧看门狗（默认 8 秒无新帧即重建管线）与自动降级，通常几秒内会自动恢复。
2. **查看降级日志**：日志里会出现"连续 N 次取帧失败，降级分辨率至 …"、"降级帧率至 …"、"回退到 RGB888 采集通路"。
3. **手动复位**：**系统** → **摄像头** → 点"切换"重建管线，或点"重启服务"。
4. **确认没有别的进程占用摄像头**：`ps aux | grep -E 'rpicam|libcamera|ffmpeg'`。

### 15.3 画面颜色偏紫 / 偏色

1. **断电重新插排线**：排线接触不良或方向装反会导致色彩通道错位。务必断电操作。
2. **换采集通路对比**：ISP 硬件 JPEG 与原始 RGB 两条通路的 ISP 处理路径不同，可以快速判断是不是通路问题。
3. **确认摄像头模组**：非官方模组或仿制模组常常没有正确的 ISP 调校，色彩会明显偏差。
4. **降低 JPEG 质量影响**：`camera.jpeg_quality` 调高到 85 以上能减轻压缩造成的色块感。

### 15.4 录像没有生成

按顺序检查：

1. **录像是否被暂停**：实时预览页"暂停录像"按钮状态；`record.paused` 配置项。
2. **侦测是否开启**：**侦测调参** → "启用移动侦测"；`motion.enabled`。
3. **事件间隔是否太长**：`record.event_gap_seconds` 默认 10 秒，两次事件太密时新移动会被吞掉。
4. **磁盘是否已满**：顶栏「磁盘」指标显示的是目标文件系统的**真实剩余空间**（空间不足时会变红）；
   `du -sh ~/pikrellcam-lite/media` 看媒体占用。超过 `max_disk_gb` 会自动删旧文件，
   剩余空间低于 `min_free_gb` 也会自动清理，仍不足则暂停录像并告警。
5. **ffmpeg 是否可用**：`which ffmpeg`；缺失时服务无法编码。
6. **看日志**：`journalctl _SYSTEMD_USER_UNIT=pikrellcam-lite.service -f | grep -i "ffmpeg\|event"`。
7. **确认事件确实被触发**：实时预览页 OSD 左下角会显示命中的算法、区域与变化占比。

### 15.5 端口被占用

```bash
# 查看是谁占着 8080
sudo lsof -i :8080
# 或
ss -ltnp | grep 8080
```

两种处理方式：

- 停掉占用进程。
- 改端口：编辑 `~/pikrellcam-lite/config.json` 的 `web.port`，然后 `systemctl --user restart pikrellcam-lite.service`。

### 15.6 摄像头被占用

日志出现 `Pipeline handler in use by another process`，说明有别的进程占着相机：

```bash
# 找出占用进程
ps aux | grep -E 'rpicam-vid|libcamera|camera-app' | grep -v grep

# 结束它
pkill -f rpicam-vid
```

常见来源：官方相机应用、`rpicam-vid` 手动测试、或另一个 pikrellcam-lite 实例。

### 15.7 权限问题

| 现象 | 处理 |
| --- | --- |
| `sudo loginctl enable-linger` 失败 | 没有 sudo 权限时手动执行一次；否则开机不会自动启动。 |
| 媒体目录无法写入 | 检查 `media.dir` 指向的目录是否对运行服务的用户可写；USB 盘建议先 `sudo chown -R $USER:$USER /mnt/usb`。 |
| `~/.pikrellcam` 权限过宽 | `chmod 700 ~/.pikrellcam`（安装脚本会自动执行）。 |
| 舵机没有反应 | 确认已启用舵机且 GPIO 引脚未与其它用途冲突；Pi 5 上建议用 `servoblaster` 或 `lgpio` 后端。 |

### 15.8 忘记密码

密码哈希保存在 `config.json` 的 `web.password_hash`。清空它即可关闭密码保护：

```bash
python3 - <<'EOF'
import json, pathlib
p = pathlib.Path.home()/"pikrellcam-lite/config.json"
c = json.loads(p.read_text()); c["web"]["password_hash"] = ""
p.write_text(json.dumps(c, indent=2))
EOF
systemctl --user restart pikrellcam-lite.service
```

### 15.9 怎么看日志

```bash
# systemd 实时日志（推荐）
journalctl _SYSTEMD_USER_UNIT=pikrellcam-lite.service -f

# 文件日志（自动轮转，保留 3 份，每份最大 2MB）
tail -f ~/pikrellcam-lite/logs/pikrellcam.log

# 服务状态
systemctl --user status pikrellcam-lite.service

# 重启服务
systemctl --user restart pikrellcam-lite.service
```

> 部分系统上 `journalctl --user` 不可用，改用 `journalctl _SYSTEMD_USER_UNIT=pikrellcam-lite.service`。
> 网页 **系统** → **实时日志** 面板也会每秒刷新同样的内容。

### 15.10 其它常见现象

| 现象 | 说明与处理 |
| --- | --- |
| 一直误报移动 | 摄像头正对显示器时屏幕内容变化会被当成移动；调高 `count_limit` 与 `magnitude_limit`，或缩小检测区域。 |
| 关灯时疯狂触发 | 帧差分对整体光照突变敏感；提高阈值或增大 `noise_filter`。 |
| 预览卡、延迟大 | 降低 `camera.fps`；USB 摄像头若只支持 YUYV 会走软件转码，CPU 开销更高。 |
| 看不到 USB 摄像头 | Debian 13 的 libcamera 枚举不到 USB 设备，需要用 V4L2 后端；在"系统 → 摄像头"里选 `/dev/videoN`。 |
| 升级按钮报错 | 部署目录不是 git 仓库，无法在线升级；改用 `deploy.sh` 发布。 |

## 16. 安全建议

1. **务必设置访问密码。** 首次安装后在 **系统** → **升级与密码** 里设置密码。默认配置是**不启用**密码保护的。
2. **不要把 8080 端口直接暴露到公网。** 服务使用 Flask 内置服务器，没有 TLS、没有请求限流、没有 CSRF 防护。
3. **需要外网访问时，请自己加反向代理**：用 Nginx / Caddy 做 HTTPS 终止、限制来源 IP、加基础认证。
4. **换掉默认端口**并不能作为安全措施，只是减少扫描命中，请配合上面的访问控制一起做。
5. **注意局域网内的其他设备。** 同网段的任何设备都能访问控制台并修改配置。
6. **密码以哈希形式存储**（`sha256:<hex>`），但配置文件本身是明文可读的，因此**不要把 `config.json` 放进公开的备份或代码仓库**。
7. **事件钩子能执行任意 shell 命令**，`/api/upgrade` 会在部署目录里执行 `git pull`。启用密码保护后务必设置一个强密码，并定期检查钩子配置。
8. **给 `~/.pikrellcam` 加权限**：`chmod 700 ~/.pikrellcam`，里面存放 FIFO 与命令配置文件。
9. **及时更新**。用 `bash deploy.sh` 发布新版本，旧版本目录会保留在 `releases/` 里——确认新版本稳定后，可以手工删除不再需要的旧版本目录来回收空间。
10. **归档到远端时使用最小权限的账号**。`media.archive_target` 指向的 SSH 账号只需要对目标目录有写权限即可。
